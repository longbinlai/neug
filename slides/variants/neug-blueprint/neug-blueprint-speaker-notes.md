# NeuG 汇报演讲稿

## 第 1 页：封面

各位好，我是赖龙彬，也可以叫我尤林。今天汇报的是 NeuG，一个面向 Agent 应用的嵌入式图数据引擎。项目地址是 https://github.com/alibaba/neug。

这次不是单纯讲一个数据库内核，而是讲我们为什么认为图数据能力会成为 LLM 和 Agent runtime 里的基础组件。整份汇报会从问题背景开始，再到 NeuG 已经具备的基础能力，最后落到三个应用场景：组织知识、业务分析，以及个人与设备记忆。

## 第 2 页：Why Now

现在 LLM 和 Agent 遇到的瓶颈，已经不只是上下文窗口够不够大。很多任务真正需要的是一层可以持续维护的关系网：文档和代码是什么关系，会议和决策是什么关系，任务和人、项目、时间又是什么关系。

这里可以先简略说一下图模型。图模型把对象表示成节点，把对象之间的关系表示成边，所以它天然适合表达“谁连接了谁、路径怎么走、上下文怎么扩展”。图数据库就是围绕这种模型做存储和查询的系统，它不只是查一条记录，而是很擅长沿关系连续探索。

所以对 LLM 和 Agent 来说，图数据库的价值在于：它可以把临时 prompt 里的上下文，变成可更新、可追溯、可分析的关系层。我们在第 6 页会把这些需求收敛成三个场景：组织知识、业务分析、个人与设备记忆。

## 第 3 页：复杂上下文需要具备混合检索能力的图引擎

如果只有向量检索，系统只能回答“哪些内容语义相似”。但 Agent 做复杂任务时，往往还要回答“这个项目是谁参与的”“这个决策来自哪次会议”“某个指标在代码里对应哪个字段”。这些问题需要关系、语义和关键词一起工作。

NeuG 在这里的定位，是把 Graph Core、Vector、Full-text、GDS 和 CLI 统一成一个可被 Agent 调用的图引擎。也就是说，关系负责扩展上下文，向量负责语义召回，全文负责精确定位，图分析负责进一步判断重要性、路径和结构。

## 第 4 页：NeuG 已经单机形态下性能最强的图数据引擎

这一页回答一个基础问题：如果 NeuG 要进入 Agent runtime，性能能不能站得住。左边是 Mac 单机上的 LDBC SNB Interactive 对比，NeuG 在这个测试里相比 Neo4j 有明显优势；右边是 LDBC-300 标准图测试，当前结果也超过官方参考成绩。

这里想强调的不是只看一个数字，而是说明 NeuG 的嵌入式形态不是以牺牲查询能力为代价。它既可以足够轻，又可以承担真实图查询负载，这样后面谈组织知识和业务分析才有底座。

## 第 5 页：21.5MB 的 pip 包，让图引擎可以进入应用和 Agent runtime

这一页讲部署形态。NeuG 当前 macOS arm64 wheel 大约 21.5MB，这个体积意味着它更接近一个可嵌入的库，而不是一个必须单独运维的图数据库集群。

这对 Agent 很关键。Agent 的执行环境可能是 CLI、脚本、skill、本地工具链，甚至未来的端侧环境。如果图能力需要额外服务和复杂运维，就很难进入这些场景。NeuG 的轻量形态让图查询和混合检索可以直接贴近 Agent 的执行现场。

## 第 6 页：NeuG Graph Core 统一承载扩展、分析与 CLI 查询

这一页把能力地图收束一下。NeuG Graph Core 是中间的统一内核，上面接 Vector Extension 和 Graph Analytics，右边通过 CLI 暴露给 Agent 或开发者使用。

下面这条能力线也对应后面的三个场景。组织知识需要混合检索和可维护知识图；业务分析需要图分析和多轮下钻；个人与设备记忆则更依赖轻量嵌入和本地关系索引。后面我会逐个展开。

## 第 7 页：组织知识，先从研发知识库切入

第一个场景是组织知识。组织知识本身很大，所以我们先选研发知识库作为切入点，因为代码、文档、模块、概念和版本之间天然有关系。

比如这里的问题：对比 MySQL、PostgreSQL 和 NeuG 在 MVCC、WAL、隔离级别和并发控制上的实现差异。如果只靠临时 RAG，很容易召回一堆切片，但它不知道哪些切片属于哪个模块、哪个仓库、哪个概念，也很难稳定回溯来源。

用 NeuG 的方式，是先把 repo、module、concept、wiki 和 raw source 建成图。Agent 提问时，先从问题里抽取概念，再沿图找到相关模块和仓库，同时用向量找相似设计、用全文锁定术语和代码符号。最后答案从 wiki 摘要返回，必要时还能沿 source 回到原始材料。

## 第 8 页：研发知识库，增量维护避免知识腐化

组织知识真正难的不是第一次建库，而是持续维护。研发知识会随着代码、接口、模块边界和设计文档不断变化。如果 wiki 不跟着更新，Agent 很快就会引用过期概念，知识库会从“有帮助”变成“不可信”。

NeuG 在这里可以把更新流程做成可控的增量维护。PR 或 release diff 先进临时图，不直接污染正式知识库；然后沿函数、模块、concept、wiki 页分析影响范围；接着生成 wiki 更新建议和 source 回溯链路；最后经过人审查，再写入正式知识库。

这页的核心是：NeuG 不只是用来查询知识，也可以管理知识的生命周期，让组织知识库不会因为更新失控而腐化。

## 第 9 页：业务分析，先从招聘与岗位变化切入

第二个场景是业务分析。这里我们先从招聘与岗位变化切入，因为岗位、职业、职级、地区和时间这些口径天然相连，很适合建成业务图。

比如问题是：AI 对美国就业的冲击有多大？如果只是一次 SQL，很容易只得到一个总量变化。但真正的分析会继续拆：是招聘数量变了，还是岗位结构变了？Junior 和 Senior 是否不同？具体落在哪些职业、地区和时间段？

NeuG 的作用是把这些分析口径变成图里的节点和边。这样 Agent 做分析时，不是每轮都重新猜口径，而是沿着已有业务图持续扩展、对比和回溯证据。

## 第 10 页：业务分析，多轮下钻天然适合图搜索

上一页讲的是业务图怎么建，这一页讲为什么多轮下钻适合图数据库。业务分析不是一问一答，而是每一轮都从当前发现继续扩展候选维度，同时保留路径状态，并剪掉低价值分支。

这和图里的 BFS 或 DFS 很像。BFS 更像广度扩展，先看整体趋势、职业、地区这些方向；DFS 更像沿一个有价值分支继续钻，比如进入计算机职业，再看 Junior、Senior 和主要州，最后落到软件开发和具体职级。

所以 NeuG 承载这类 workload 是自然的：它能保存分析路径，支持关系扩展，也能把中间结果沉淀下来，避免 Agent 每一轮都从 prompt 里重新组织上下文。

## 第 11 页：个人与设备记忆，从小场景验证端侧关联索引

第三个方向目前还没有作为主线实现，所以这一页只讲潜在切入点。我们不直接从设备形态出发，而是从个人高频、数据边界清楚的小场景验证。

比如会后任务记忆，可以把会议纪要、IM、日历和 PR 关联到人、项目和截止时间；个人资料回溯，可以把本地文档、代码片段和浏览记录抽取成摘要、来源和任务关系；设备事件索引，则可以记录轻量事件，例如见了谁、在哪、关联哪件事。

这些场景共同的特点是关系清楚、数据本地性强，而且 prompt 历史很难长期维护。NeuG 的轻量嵌入能力，为未来个人与设备记忆保留了端侧关联索引的入口。

## 第 12 页：Roadmap

最后收束一下。近期重点不是铺太多方向，而是先把两个可展示闭环打磨出来：一个是组织知识闭环，一个是业务分析闭环。

组织知识闭环会围绕 Vector、full-text、GDS 和 CLI，做企业知识库或代码知识库的演示验证。业务分析闭环会围绕数据湖接入、采样和 NeuGBI，把招聘或经营分析跑成端到端演示。

整体结论是：NeuG 不是单点图数据库，而是面向 LLM 和 Agent 的嵌入式图数据底座。下一步先把组织知识和业务分析两个闭环做扎实，再选择一个个人记忆小场景做轻量验证。

## 第 13 页：Q&A

最后进入 Q&A。这里可以围绕三个问题展开：第一，组织知识和 NeuGBI 两个闭环，哪个更适合作为第一阶段演示；第二，混合检索、图分析、采样和 CLI 哪些能力需要优先稳定；第三，NeuG 作为嵌入式图引擎，应该先接入哪些 Agent runtime 或工具链。
