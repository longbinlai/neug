# NeuG 汇报演讲稿

## 第 1 页：封面

各位好，我是赖龙彬，也可以叫我尤林。今天汇报的是 NeuG，一个面向 Agent 应用的嵌入式图数据引擎。项目地址是 https://github.com/alibaba/neug。

这次不是单纯讲一个数据库内核，而是讲我们为什么认为图数据能力会成为 LLM 和 Agent runtime 里的基础组件。整份汇报会从问题背景开始，再到 NeuG 已经具备的基础能力，最后落到三个应用场景：组织知识、业务数据分析，以及个人与设备记忆。

## 第 2 页：Why Now

现在 LLM 和 Agent 遇到的瓶颈，已经不只是上下文窗口够不够大。很多任务真正需要的是一层可以持续维护的关系网：文档和代码是什么关系，会议和决策是什么关系，任务和人、项目、时间又是什么关系。

这里可以先简略说一下图模型。图模型把对象表示成节点，把对象之间的关系表示成边，所以它天然适合表达“谁连接了谁、路径怎么走、上下文怎么扩展”。图数据库就是围绕这种模型做存储和查询的系统，它不只是查一条记录，而是很擅长沿关系连续探索。

所以对 LLM 和 Agent 来说，图数据库的价值在于：它可以把临时 prompt 里的上下文，变成可更新、可追溯、可分析的关系层。我们在第 6 页会主要介绍和公司业务密切相关的三个场景：组织知识、业务数据分析、个人与设备记忆。

## 第 3 页：复杂上下文需要具备混合检索能力的图引擎

如果只有向量检索，系统只能回答“哪些内容语义相似”。但 Agent 做复杂任务时，往往还要回答“这个项目是谁参与的”“这个决策来自哪次会议”“某个指标在代码里对应哪个字段”。这些问题需要关系、语义和关键词一起工作。

NeuG 在这里的定位，是把 Graph Core、Vector、Full-text、GDS 和 CLI 统一成一个可被 Agent 调用的图引擎。也就是说，关系负责扩展上下文，向量负责语义召回，全文负责精确定位，图分析负责进一步判断重要性、路径和结构。

## 第 4 页：NeuG 是单机形态下性能最强的图数据引擎

这一页回答一个基础问题：如果 NeuG 要进入 Agent runtime，性能能不能站得住。左边是 Mac 单机上的 LDBC SNB Interactive 对比，NeuG 在这个测试里相比 Neo4j 有明显优势；右边是 LDBC-300 标准图测试，当前结果也超过官方参考成绩。

这里想强调的不是只看一个数字，而是说明 NeuG 的嵌入式形态不是以牺牲查询能力为代价。它既可以足够轻，又可以承担真实图查询负载，这样后面谈组织知识和业务数据分析才有底座。

## 第 5 页：21.5MB 的 pip 包，让图引擎可以进入应用和 Agent runtime

这一页讲部署形态。NeuG 当前 macOS arm64 wheel 大约 21.5MB，这个体积意味着它更接近一个可嵌入的库，而不是一个必须单独运维的图数据库集群。

这对 Agent 很关键。Agent 的执行环境可能是 CLI、脚本、skill、本地工具链，甚至未来的端侧环境。如果图能力需要额外服务和复杂运维，就很难进入这些场景。NeuG 的轻量形态让图查询和混合检索可以直接贴近 Agent 的执行现场。

## 第 6 页：NeuG Graph Core 统一承载扩展、分析与 CLI 查询

这一页把能力地图收束一下。NeuG Graph Core 是中间的统一内核，上面接 Vector Extension 和 Graph Analytics，右边通过 CLI 暴露给 Agent 或开发者使用。

下面这条能力线也对应后面的三个场景。组织知识需要混合检索和可维护知识图；业务数据分析需要图分析和多轮下钻；个人与设备记忆则更依赖轻量嵌入和本地关系索引。后面我会逐个展开。

## 第 7 页：组织知识，先从研发知识库切入

第一个场景是组织知识。组织知识本身很大，所以我们先选研发知识库作为切入点，因为代码、文档、模块、概念和版本之间天然有关系。

比如这里的问题：对比 MySQL、PostgreSQL 和 NeuG 在 MVCC、WAL、隔离级别和并发控制上的实现差异。如果只靠临时 RAG，很容易召回一堆切片，但它不知道哪些切片属于哪个模块、哪个仓库、哪个概念，也很难稳定回溯来源。

用 NeuG 的方式，是先把 repo、module、concept、wiki 和 raw source 建成图。Agent 提问时，先从问题里抽取概念，再沿图找到相关模块和仓库，同时用向量找相似设计、用全文锁定术语和代码符号。最后答案从 wiki 摘要返回，必要时还能沿 source 回到原始材料。

## 第 8 页：研发知识库，把每次提交变成可维护的知识更新

组织知识真正难的不是第一次建库，而是持续维护。研发知识会随着代码、接口、模块边界和设计文档不断变化，所以维护流程要能跟着每次提交更新一起走。

这页按照一条变更链路来讲。第一步是提交更新，函数、接口、文档和配置会产生新关系，这时不能直接写正式知识库，而是先进入临时图隔离验证。第二步是影响定位，变更可能牵动模块、concept 和 wiki 页面，NeuG 可以沿这些关系扩展，标记哪些页面和答案需要维护。第三步是审查入库，更新建议带着来源链路给人确认，再合并到正式图。

这页的核心是：NeuG 不只是用来查询知识，也可以管理知识的生命周期。维护单元从整库重写变成每次提交更新，研发知识库才能随着代码一起增量演进。

## 第 9 页：业务数据分析，先从招聘与岗位变化切入

第二个场景是业务数据分析。这里我们先从招聘与岗位变化切入，因为岗位、职业、职级、地区和时间这些口径天然相连，很适合建成业务图。

比如问题是：AI 对美国就业的冲击有多大？如果只是一次 SQL，很容易只得到一个总量变化。但真正的分析会继续拆：是招聘数量变了，还是岗位结构变了？基础岗位和资深岗位是否不同？具体落在哪些职业、地区和时间段？

NeuG 的作用是把这些分析口径变成图里的节点和边。这样 Agent 做分析时，不是每轮都重新猜口径，而是沿着已有业务图持续扩展、对比和回溯证据。

## 第 10 页：业务数据分析，从开放问题下钻到软件开发 L2

上一页讲的是业务图怎么建，这一页把一次具体分析放进一棵树里。根问题是：AI 影响了哪些美国岗位？数据来自 Revelio 2021 到 2025 年的美国就业记录，规模是 60GB、3 亿条。这里不是一上来给一个总量答案，而是先把问题变成可下钻的分析树。

第一轮先看整体趋势。这里的总量只是全量记录层面的背景，它混着数据覆盖、市场周期和岗位结构变化，不能和后面按资历层级拆出来的降幅直接对齐。它的作用只是告诉我们：数据里确实有下降信号，但不能在总量上结束分析。

第二轮按资历层级拆开：基础岗位 L1 到 L2 下降 29.4%，资深岗位 L3 以上下降 5.8%。这一步把问题从“整体是否下降”推进到“下降更集中在基础岗位”。所以树的主干继续沿基础岗位往下走。

第三轮在基础岗位里按职业方向继续拆。这里不是泛泛地看所有岗位，而是把职业作为下一层分支，选中下降明显、也更贴近 AI 影响讨论的计算机相关职业。这个分支在 2022 到 2024 年间，招聘数量下降 64%，所以值得继续下钻到具体岗位。

再往下落到软件开发岗位和职级，软件开发 L2 从 280 万降到 145 万，而 L1 和 L3 以上基本稳定。这样结论就从一个开放问题收敛成一个可解释的业务发现：软件开发 L2 职级下降最明显。

树上的灰色分支不是废弃信息，而是复核节点。比如总体基线负责校准问题规模，地区和时间切片负责检查趋势是否稳定，避免把覆盖率波动或单点异常误读成业务结论。NeuG 的价值就在这里：它保存的不是一句答案，而是整棵可复用分析树。每个问题节点、采样发现、证据来源、旁路判断和剪枝理由都留在图里，Agent 下一轮可以从任一节点继续展开。

## 第 11 页：个人与设备记忆，千问眼镜需要端侧关系图

第三个方向目前还没有作为主线实现，但它不是泛泛的“个人知识库”。更具体的入口是千问眼镜这类随身设备。眼镜会看到人、地点、画面、文字和对话，也会产生后续任务。这里天然不是一条线性的聊天历史，而是一张关系网。

比如一次客户现场交流，设备可能捕获到对话摘要、白板内容、图片线索、时间地点和参与人。NeuG 可以把这些抽成 Event、Person、Place、Artifact、Task 等节点，再用边把它们连起来。这样用户后来问“上次客户现场提到的兼容问题是什么”，Agent 就不是在 prompt 历史里硬翻，而是沿着人、地点、时间、材料和任务做多跳找回。

这个方向还强调端侧可控。个人记忆不能简单地把原始音视频长期塞进云端或 prompt 里，更合理的是沉淀轻量摘要、来源和关系边，并支持按项目、人、时间删除、回滚和复核。NeuG 的价值就是在设备侧提供一个可解释、可维护的关系索引。

## 第 12 页：Roadmap

最后收束一下。近期重点不是铺太多方向，而是先把两个可展示闭环打磨出来：一个是组织知识闭环，一个是业务数据分析闭环。

组织知识闭环会围绕 Vector、full-text、GDS 和 CLI，做企业知识库或代码知识库的演示验证。业务数据分析闭环会围绕数据湖接入、采样和 NeuGBI，把招聘或经营分析跑成端到端演示。

整体结论是：NeuG 不是单点图数据库，而是面向 LLM 和 Agent 的嵌入式图数据底座。下一步先把组织知识和业务数据分析两个闭环做扎实，再选择一个个人记忆小场景做轻量验证。

最后进入 Q&A。这里可以围绕三个问题展开：第一，组织知识和 NeuGBI 两个闭环，哪个更适合作为第一阶段演示；第二，混合检索、图分析、采样和 CLI 哪些能力需要优先稳定；第三，NeuG 作为嵌入式图引擎，应该先接入哪些 Agent runtime 或工具链。
